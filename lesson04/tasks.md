# Занятие 04. Задачи для самостоятельного решения

В этом занятии уровни обозначают объём инженерной работы. Задания можно выполнить в отдельном учебном репозитории или, где это уместно, в репозитории группового проекта. Не публикуйте секреты, токены и содержимое виртуального окружения.

## Easy 1. Паспорт задачи

Создайте файл `PROJECT_BRIEF.md`, который отвечает на шесть вопросов:

1. Кто пользователь?
2. Какую конкретную проблему он решает?
3. Какие данные поступают на вход?
4. Какой наблюдаемый результат получается на выходе?
5. По какому критерию минимальную версию можно признать работающей?
6. Что сознательно не входит в первую версию?

Пример фрагмента:

```markdown
## Пользователь
Аналитик небольшой торговой компании.

## Проблема
Нужно находить первую транзакцию с указанной суммой в выгрузке.

## Критерий успеха
CLI принимает путь и сумму, печатает индекс или -1 и обрабатывает файл из 100 000 строк.
```

Ограничения:

- не называть технологию вместо проблемы: «сделать бота» недостаточно;
- первая версия должна быть реализуема за время курса;
- каждый раздел содержит не менее одного проверяемого утверждения.

Критерии проверки:

- пользователь и его действие названы явно;
- вход и выход можно показать на демонстрации;
- критерий успеха измерим;
- перечислены хотя бы два ограничения первой версии.

## Easy 2. Чистое предметное ядро

Выберите одну функцию из предыдущих занятий и перенесите её в модуль `src/<package_name>/core.py`. Функция должна получать обычные значения Python и возвращать результат без чтения файлов, `input`, `print` и завершения процесса.

Пример контракта:

```python
def find_transaction(amounts: list[int], target: int) -> int:
    ...
```

Добавьте рядом не менее четырёх проверок через `assert` или smoke-тест: пустой вход, обычный случай, граничный случай и отсутствие результата.

Ограничения:

- Python 3.14;
- у функции есть аннотации параметров и результата;
- внешние зависимости не требуются;
- предметная функция не знает о CLI и расположении файлов.

Критерии проверки:

- функцию можно вызвать из Jupyter или другого модуля;
- проверки выполняются без интерактивного ввода;
- ошибки внешней среды не смешаны с предметным вычислением.

## Easy 3. Каркас устанавливаемого пакета

Создайте структуру:

```text
project/
├── pyproject.toml
├── README.md
├── .gitignore
├── src/
│   └── package_name/
│       ├── __init__.py
│       └── core.py
└── tests/
    └── test_smoke.py
```

В `pyproject.toml` укажите имя, версию `0.1.0`, `requires-python = ">=3.14"`, build backend и настройки Ruff. В `.gitignore` исключите `.venv/`, `__pycache__/`, `.pytest_cache/`, `.ruff_cache/` и служебные файлы редактора.

Пример проверки после установки:

```bash
python -m pip install -e .
python -c "import package_name"
```

Критерии проверки:

- импорт работает из корня проекта после установки;
- код находится под `src/`, а не рядом с `pyproject.toml`;
- виртуальное окружение не попало в Git;
- README содержит команды создания окружения и установки.

## Medium 1. Воспроизводимый CLI

Добавьте модуль `src/<package_name>/cli.py` с функцией `main() -> int` и console entry point в `[project.scripts]`. CLI принимает входные параметры, вызывает предметное ядро и печатает результат. Ошибка пользовательского ввода должна приводить к понятному сообщению в `stderr` и ненулевому коду возврата.

Пример интерфейса:

```console
$ search-tool data/numbers.txt 42
5

$ search-tool missing.txt 42
error: file not found: missing.txt
```

Добавьте воспроизводимую последовательность проверки:

```bash
python -m pip install -e ".[dev]"
ruff check .
ruff format --check .
pytest
search-tool --help
```

Ограничения:

- CLI не содержит реализацию поискового или предметного алгоритма;
- путь и пользовательские ошибки обрабатываются на границе приложения;
- повторная установка в чистое окружение не требует ручного изменения `PYTHONPATH`.

Критерии проверки:

- entry point появляется после установки;
- успешный и ошибочный сценарии имеют разные коды возврата;
- `ruff` и smoke-тест проходят;
- README содержит точные команды запуска.

## Medium 2. Две ветки и осмысленный конфликт

Выполните две независимые доработки в отдельных ветках. В первой уточните описание пользователя в README, во второй измените тот же фрагмент и добавьте критерий успеха. Слейте обе ветки в основную, разрешите возникший конфликт вручную и сохраните полезные части обоих вариантов.

Пример истории:

```text
*   merge: resolve README conflict
|\
| * docs: add measurable success criterion
* | docs: clarify target user
|/
*   chore: create project skeleton
```

Дополните `PROJECT_BRIEF.md` ссылкой на репозиторий и распределением ответственности в группе.

Ограничения:

- не использовать принудительную перезапись истории для скрытия конфликта;
- не коммитить строки `<<<<<<<`, `=======`, `>>>>>>>`;
- обе ветки содержат отдельные осмысленные коммиты;
- итоговый README читается как единый текст.

Критерии проверки:

- `git log --graph --oneline --all` показывает обе ветки и merge commit;
- в основной ветке нет незавершённого конфликта;
- сохранён смысл обеих доработок;
- репозиторий содержит паспорт задачи, каркас пакета и инструкцию запуска.

## Формат сдачи

Отправьте ссылку на репозиторий и укажите commit, соответствующий сдаваемому состоянию. В корне должны находиться `PROJECT_BRIEF.md`, `README.md`, `pyproject.toml`, `src/` и `tests/`. Для группового проекта отдельно перечислите вклад каждого участника.
